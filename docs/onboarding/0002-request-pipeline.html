The Request Pipeline, Hop by Hop

What actually happens to a request once it's inside the Node plane — the seven gates it passes, in order, and what stops it at each. ~10 min.

Warm-up (cold recall from L01 — no peeking): what two things travel on the arrow from the edge plane to the Node plane?
check yourself

A per-hop Entra M2M token (aud=api://llm-gateway-internal) plus the forwarded X-Principal-* claim headers. The Node side trusts the claims because the hop is gated by YARP's M2M token.

Win: you can recite the seven hops in order from memory, say what each one sets for later hops and what status code it rejects with — and spot the two hops that are quietly doing the same work twice.

1 · The chain, as actually wired

From services/gateway/src/app.ts. Two hops are wired app-wide (api.use('*', …)); the rest are per-route on each /v1/* POST. Order is the order they run:

1

auth

pipeline/auth.ts

Bearer present? Verify the YARP M2M token. Reject duplicate/case-variant X-Principal-* (header hygiene). Parse the forwarded claims.

sets → userAuth  ·  reject → 401 (any failure)

2

tenantContext

pipeline/tenant-context.ts

Look up the principal in the config store → resolve its model allowlist and budget policy (project- or user-scoped).

sets → tenantContext  ·  reject → 403 (no budget policy configured)

3

protocolGuard

pipeline/protocol-guard.ts

Parse the JSON body once; pull out model; tag the route's protocol family.

sets → model, parsedBody, family  ·  reject → 400 (invalid json / missing model)

4

scope

pipeline/scope.ts

Is model in this principal's modelAllowlist? (Now possible — model known from hop 3, allowlist from hop 2.)

reject → 403 (model not allowed for principal)

5

rateLimit

pipeline/rate-limit.ts

Estimate tokens; atomic checkAndConsume against RPM and token-aware TPM in Redis.

reject → 429 (rpm_exceeded / tpm_exceeded)

6

budget

pipeline/budget.ts

Sync policy → Redis. Estimate cost, multiply by 1.2×, atomically reserve microdollars with a TTL. This is a pre-flight hold, not the final charge.

sets → reservationId, budgetScope, reservedMicro  ·  reject → 429 (insufficient_quota)

7

handler → meter

features/llm/handler.ts · pipeline/meter.ts

Proxy upstream (Azure). On return: compute real cost, commit/release the reservation, then emit a usage event → queue (or WAL on failure). Meter is inside the handler, not a chain middleware.

emits → UsageEvent → Storage Queue | WAL

Mental model: hops 1–2 establish who (identity + their policy), hops 3–4 establish what (which model, allowed?), hops 5–6 establish can-they-afford-it (rate + money), hop 7 does the work and accounts for it. Each hop only runs because the previous hop set a context variable it needs.

5 · Strength & weakness (mission lens)

Strength

Strict fail-closed ordering: cheap rejects first (auth, json), expensive Redis ops last. Each hop has one job and communicates only through typed context vars — easy to test in isolation, easy to reorder. No model work happens before the caller is known and the model is allow-listed.

Weakness / smell

estimateRequestTokens runs twice (hop 5 and hop 6) — duplicated work. budget re-syncBudgetPolicy to Redis on every request (config-store cache softens it, but still hot-path). And TPM/budget both consume on an estimate, reconciled to actuals only at hop 7 — transient over-hold, cleaned by the reservation TTL.

6 · Blank-page self-test

Trace a chat request from bytes-in to usage-event. Reveal model answer.

1 auth: verify M2M, hygiene-check + parse X-Principal-* → userAuth (else 401). 2 tenantContext: config-store lookup → modelAllowlist + budgetPolicy (else 403). 3 protocolGuard: parse body, get model + family (else 400). 4 scope: model ∈ allowlist? (else 403). 5 rateLimit: RPM + token-aware TPM checkAndConsume (else 429). 6 budget: sync policy, estimate cost ×1.2, reserve micro w/ TTL → reservationId (else 429). 7 handler: proxy Azure → commit/release reservation → emit UsageEvent to Queue (WAL on failure).
