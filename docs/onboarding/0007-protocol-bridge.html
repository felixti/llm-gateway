The Protocol Bridge — Chat ⇄ Responses

1 · The problem it solves

Clients speak one of two OpenAI protocols: Chat Completions (messages[]) or Responses API (input). But each Azure deployment only speaks one of them — codex models are Responses-API-native. The model registry records each model's upstreamApi. The bridge makes the client's protocol independent of the deployment's requirement.

client protocol (route) model upstreamApi bridge? ───────────────────── ──────────────── ────── openai-chat ───────► chat-completions no (pass through) openai-chat ───────► responses YES (chat → responses → back) openai-responses ───────► responses no openai-responses ───────► chat-completions YES (responses → chat → back) needsProtocolBridge = routeProtocolToUpstream(route) !== upstream

2 · Four transforms, two dispatchers

A bridge is symmetric: translate the request on the way up, and the response on the way back. Two directions × two halves = four pure functions, picked by two dispatchers (adaptRequestBody, adaptResponseBody) keyed on (route, upstream):

DirectionRequest transform (up)Response transform (back)
chat client → responses modeltransformChatCompletionsToResponsestransformResponsesToChatCompletionsResponse
responses client → chat modeltransformResponsesToChatCompletionstransformChatCompletionsToResponse

3 · What actually gets remapped

The translation is structural — same intent, different field shapes:

Chat Completions↔Responses API
messages: [{role, content}]↔input: [{type:'message', role, content}] (or a bare string)
role system↔role developer
tool_calls on assistant↔{type:'function_call', call_id, name, arguments}
role tool + tool_call_id↔{type:'function_call_output', call_id, output}
max_completion_tokens / max_tokens↔max_output_tokens
reasoning_effort↔reasoning: { effort }
finish_reason: tool_calls|stop↔derived from whether output has function calls
A nice touch: transformChatCompletionsToResponses collapses a single user-text message into a bare string input (the simplifiedInput path) — matching how the Responses API is normally called by hand. And stringifyContent flattens array/multimodal content down to text.

4 · The one thing it refuses

From L06: when a bridge is needed and the client asked for stream:true, the upstream client returns 400 streaming_protocol_bridge_unsupported. Translating a live SSE stream between two different event schemas isn't built — so it fails fast and loud rather than silently mangling the stream. Honest fail-closed, again.

6 · Strength & weakness (mission lens)

Strength

Textbook adapter pattern: four small pure functions, dispatched by a 2×2 table, fully unit-testable in isolation (responses-chat-bridge.test.ts). It decouples client protocol from deployment capability — one client integration reaches heterogeneous Azure models. Fails closed on the case it can't honour (bridge+stream).

Weakness / limit

The translation is lossy: stringifyContent flattens multimodal/array content to plain text — non-text parts are dropped. Response transforms inject hardcoded defaults (temperature:1, top_p:1, tool_choice:'auto') that may not reflect the real request. And no streaming across the bridge at all (L06). Fine for text+tools today; watch it as multimodal grows.
