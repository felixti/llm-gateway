Lesson 01 · Architecture / the WHY

The Two-Plane Architecture

Why your gateway is split into a .NET edge and a Node brain — and what that split bought and cost. ~8 min.

Win for this lesson: after this you can sketch the two planes on a blank page, say what each one owns, and defend why they're separate against the obvious "just use one service" objection. That defence is the heart of owning this system.

1 · The one decision everything hangs off

Your system makes one structural choice before any other: governance is split across two planes, connected by one trusted hop. Almost every other design decision is downstream of it.

client ──(Entra JWT, aud = edge)──► ┌───────────────────────────┐ │ EDGE PLANE .NET 10 YARP │ identity / transport │ • validate user token │ │ • OBO · per-principal RPM │ │ • strip + set X-Principal │ └────────────┬──────────────┘ per-hop M2M token + forwarded │ X-Principal-* (aud = internal) ▼ ┌───────────────────────────┐ │ LLM-DOMAIN Node 24 Hono │ LLM-specific │ • USD budget · token TPM │ │ • guardrails · resilience │ │ • provider routing/meter │ └────────────┬──────────────┘ ▼ Azure OpenAI / Foundry

The dividing line is a single question: is this governance LLM-specific, or generic?

Edge plane — generic

services/edge · .NET 10 · YARP

  • Entra user-token validation (delegated + app-only)
  • OBO minting (for KB)
  • Per-principal RPM (coarse)
  • Governance routing
  • Sets X-Principal-* claims

LLM-domain plane — specific

services/gateway · Node 24 · Hono

  • USD quota / budget
  • Token-aware TPM (needs tiktoken)
  • Guardrails + reversible PII
  • Provider resilience / fallback
  • FinOps cost + WAL

2 · Why split it (the defence)

Three reasons, straight from ADR-0009:

  • Some governance is irreducibly LLM-domain. USD quota, token-aware limits, guardrails, and cost need to parse LLM tokens/cost/content. They cannot live in .NET without re-implementing tiktoken, pricing, and a protocol-aware PII walker in C#.
  • Moving auth to YARP deletes risk, not just relocates it. A hand-rolled Entra verifier was flagged High-risk. Microsoft.Identity.Web gives validation, JWKS, OBO, and token caching as first-party code. The Node side is left with a trivial check: one issuer + one appid + one audience.
  • Org standard. YARP/.NET is the platform's reverse-proxy + identity stack — reuse ops and app-registration tooling.
The rejected alternative SP-C — "put all governance in YARP" — was killed precisely because it would re-implement tiktoken/pricing/PII in .NET and create two sources of truth. The mirror alternative SP-B — "keep auth in Node, YARP is transport-only" — was killed because it keeps the fragile hand-rolled verifier. The split threads between both.

5 · Blank-page self-test

Cover the screen. On paper, draw the two boxes and the arrow between them. Label: the runtime of each, two responsibilities each, and what travels on the arrow. Then check:

Reveal the model answer

Edge (.NET 10 / YARP): validate Entra user token · OBO · per-principal RPM · routing · sets X-Principal-*.
LLM-domain (Node 24 / Hono): USD budget · token-aware TPM · guardrails/PII · resilience/fallback · FinOps/WAL.
On the arrow: a per-hop Entra M2M token (aud = api://llm-gateway-internal, YARP's appid) plus the forwarded X-Principal-* claim headers. The Node side never re-validates the user token (wrong audience) — it trusts the claims because the hop is gated by YARP's M2M token.

6 · Strength & weakness (your mission lens)

Strength

Each plane has a small, testable responsibility in the runtime that's best for it. Auth risk is deleted by using first-party Entra code, not relocated. One choke point per concern → one source of truth.

Weakness / cost

Two runtimes, two skill-sets, +1 hop. And the split creates a new top risk: header spoofing — the Node side trusts X-Principal-* blindly, so the whole security model leans on network isolation + the M2M appid pin (no mTLS). That's L03.
