The Trust Model — No mTLS, No Problem?

The Node plane blindly trusts identity headers. That sounds insane. This lesson is why it's actually safe — and exactly where it isn't. ~11 min.

1 · The uncomfortable fact

The Node plane never validates the end user's Entra token. It can't — that token's audience is api://ai-gateway-edge (the edge), not the gateway. Instead the gateway reads who the caller is straight out of plain HTTP headers (X-Principal-Id etc.) and believes them. The operator also refused mTLS between internal services.

So: forge an X-Principal-Id header → become anyone? That is the threat this whole model exists to close. The answer is defense in depth, not a single wall.

Edge does 3 things

  1. Strip inbound identity headers
  2. Set trusted ones from validated claims
  3. Attach its own M2M bearer token

A caller cannot get a header past YARP that YARP didn't set.

Node does 3 checks

  1. Verify the M2M token (only YARP's appid)
  2. Hygiene: no dup/case-variant headers
  3. Parse: strict shape or 401

Never "best-effort parses" identity — malformed = reject.

3 · The four defense layers (ADR-0009 M0 hardening)

For a forged-identity attack to land, an attacker must beat all of these:

① Network isolation — k8s NetworkPolicy: the gateway accepts ingress only from pods labelled app: edge, port 3000. Can't even reach Node from elsewhere. (primary control — replaces mTLS)
② M2M token pin — Node accepts only iss=tenant v2.0, aud=api://llm-gateway-internal, appid|azp=YARP's exact app id. No YARP credential ⇒ no entry.
③ Header hygiene — reject duplicate/case-variant X-Principal-*; strict claim shape; malformed ⇒ 401. Closes header-injection smuggling.
④ JWS-signed claim set — YARP signs the X-Principal-* set, Node verifies the signature. Recommended, NOT yet implemented. This is the accepted residual gap.
The threat — a forged X-Principal-Id — dies at layer ① for an external attacker (can't reach the pod) and at ②+③ for anything coming through the front door (no M2M token / stripped headers). Layer ④ is what would close the insider path: a compromised in-cluster workload that already holds a valid M2M token could still spoof claims today. That's the real, documented weakness.

6 · Strength & weakness (mission lens)

Strength

No mTLS ops burden, yet not naïve: four independent layers, any one of which defeats the obvious attack. Identity validation uses first-party Entra code in YARP, not a hand-rolled verifier. Node's check is trivial and hard to get wrong (one issuer, one appid, one audience). Fail-closed on malformed claims.

Weakness / debt

Trust is soft: any holder of a valid M2M token can forge claims, because layer ④ (JWS) isn't built — the boundary leans on network isolation + "only YARP has the credential." Also an M0 hack: a SP's project is carried in the Entra roles claim (// M0: project carried via app role) — overloaded, needs a real project claim later.

7 · Blank-page self-test

Draw the boundary: 3 things YARP does, 3 checks Node does, 4 defense layers, 1 gap. Reveal.

YARP: strip inbound X-Principal-* → set trusted from validated Entra claims → attach its own M2M bearer.
Node: verify M2M (iss+aud=internal+appid=YARP) → header hygiene (no dup/case-variant) → strict shape-parse (else 401).
Layers: ① NetworkPolicy (edge-only ingress) · ② M2M pin · ③ header hygiene · ④ JWS-signed claims.
Gap: ④ not implemented → a valid-M2M insider can still spoof claims (accepted residual).
